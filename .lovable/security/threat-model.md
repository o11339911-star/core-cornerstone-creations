# نموذج التهديد وحدود الثقة — منصة ركيز (27A)

## 1) حدود الثقة

```text
[1] المستخدم/الجهاز
      │ كلمة مرور فقط (لا عامل ثانٍ: auth.mfa_factors = 0)
      ▼
[2] Supabase Auth (GoTrue v2.195.0) — email/password فقط، disable_signup=false
      │ Access JWT (مدة غير محسومة) + Refresh Token
      ▼
[3] العميل (React) — الجلسة في localStorage، attachSupabaseAuth يرفق Bearer
      │
      ▼
[4] TanStack Server Fns — requireSupabaseAuth يتحقق من التوكن عبر getUser()، CSRF middleware مفعّل
      │ يعمل بصلاحيات المستخدم (لا service role في المسار العادي)
      ▼
[5] الحساب النشط (active-account) — اختيار كيان؛ حدّ منطقي في الواجهة
      ▼
[6] الكيان → المشروع → الطرف: يُنفَّذ فعليًا في القاعدة عبر RLS + private.can (الوحدة والفعل معًا)
      ▼
[7] Postgres 17.6 — RLS على كل جداول public، 247 دالة public + 93 private بـ SECURITY DEFINER وsearch_path مثبّت
      ▼
[8] Storage — سياسات على storage.objects (وسائط 360 خام/عامة)
      ▼
[9] التكاملات الخارجية — mock فقط، أسماء متغيرات بيئة في القاعدة، sanitize_error على الرسائل
```

## 2) ما الذي يُتحقق منه عند كل حد — وأين الفجوة

| الحد | التحقق القائم اليوم | الفجوة |
|---|---|---|
| 1→2 | كلمة مرور + تأكيد بريد | لا عامل ثانٍ؛ حماية كلمات المرور المسرّبة معطّلة؛ التسجيل الذاتي مفتوح على مستوى الخدمة |
| 2→3 | JWT موقّع | مدة JWT غير محسومة؛ لا سقف جلسات؛ 137 جلسة يتيمة لم تُنظَّف |
| 3→4 | CSRF middleware + Bearer | لا تحقق AAL ولا حداثة جلسة قبل العمليات الحساسة |
| 4→7 | `requireSupabaseAuth` + RLS + `private.can` | **لا فجوة بنيوية معروفة** — أقوى طبقة في النظام |
| 7→8 | سياسات storage.objects | لا حدّ معدل على الرفع |
| 7→9 | sanitize_error + حارس الأسرار | لا تنبيهات على الفشل المتكرر خارج عدادات التكاملات |
| عرضي | — | لا `security_events`، ولا سجل تدقيق Auth (`audit_log_entries` = 0) |

## 3) الخصوم المعتبرون

1. **مهاجم خارجي بلا حساب**: حشو بيانات اعتماد، إساءة نقطة signup المفتوحة، إساءة مسارات استعادة كلمة المرور/الدعوات (استنزاف SMTP).
2. **مستخدم شرعي يحاول تجاوز نطاقه**: كيان آخر، مشروع آخر، ملف آخر — تُقابله RLS و`private.can` (تُثبت سلبيًا في 27H).
3. **جهاز/جلسة مسروقة**: لا وسيلة اليوم داخل المنتج لإنهاء الجلسات، ولا عامل ثانٍ يوقف الاستخدام.
4. **موظف منصة مخترق**: أعلى أثر (وصول عابر للمستأجرين عبر Break-glass) وبلا AAL2.
5. **خطأ تشغيلي/فقد بيانات**: بلا RPO/RTO معتمدين ولا اختبار استعادة موثّق.

## 4) مصفوفة المخاطر (بعد أدلة 27A)

**Critical**
- **C1 — التسجيل الذاتي مفتوح على مستوى الخدمة** (`disable_signup=false`) بينما المنصة بالدعوة فقط. الأثر: حسابات غير مدعوّة، إساءة موارد. المعالجة: 27B، إعداد لوحة، بلا أثر على أحد.
- **C2 — لا عامل ثانٍ لأي دور حساس** (0 عوامل، 0 جلسات aal2). المعالجة: 27C.

**High**
- **H1 — لا مسار إنهاء جلسات** داخل المنتج + 137 جلسة يتيمة و0 `not_after`. المعالجة: 27B.
- **H2 — حماية كلمات المرور المسرّبة معطّلة** (ناتج فحص Supabase). المعالجة: 27B.
- **H3 — لا اختبار استعادة ولا RPO/RTO معتمدان تقنيًا** (المالك أقرّ Pilot 24س/8س ثم 1س/4س). المعالجة: 27G.
- **H4 — لا تنبيهات أمنية ولا سجل أحداث أمني**؛ `auth.audit_log_entries` = 0. المعالجة: 27F.

**Medium**
- **M1 — لا حدّ معدل تطبيقي** على الدعوات والرسائل والرفع وطلبات DSR (حدود GoTrue المدمجة تغطي مسارات Auth فقط). المعالجة: 27D.
- **M2 — CAPTCHA غير مفعّلة** على الدخول/الاستعادة. المعالجة: 27D (إعداد لوحة).
- **M3 — SMTP غير محسوم**؛ المدمج محدود المعدل ويكسر الدعوات عند التوسع. المعالجة: 27D/27G.
- **M4 — لا سياسة تدوير أسرار مكتوبة** (رغم صحة القاعدة: أسماء متغيرات فقط). المعالجة: 27E.
- **M5 — `platform_staff` = 0**: لا أحد يملك اليوم وصول لوحة المنصة؛ قرار تشغيلي مطلوب. المعالجة: قرار مالك.

**Low**
- **L1 — لا عرض «آخر دخول/جهاز» للمستخدم.** 27B.
- **L2 — تنبيها الفاحص عن دوال SECURITY DEFINER** مطابقان للتصميم المقصود؛ يوثَّقان في ذاكرة الأمن بدل معالجتهما. 27E.
- **L3 — لا `pg_cron`/`pg_net`**: أي مهام دورية أمنية تحتاج مسار `/api/public/cron/*` القائم. 27F.

## 5) تصحيحات مُعتمدة أُدمجت في النموذج

- **إبطال الجلسات** يتم عبر واجهات Supabase الرسمية `supabase.auth.signOut({ scope: 'local' | 'others' | 'global' })` حصرًا. **ممنوع** الحذف المباشر من `auth.sessions` أو `auth.refresh_tokens`.
- **إبطال Refresh Token ليس ضمانًا فوريًا**: Access JWT الحالي يبقى صالحًا حتى انتهاء مدته. لذلك العمليات شديدة الحساسية تتطلب **تحققًا حديثًا من `session_id`** (مطالبة `session_id` داخل التوكن تُقارن بجلسة قائمة) وليس مجرد وجود توكن صالح.
- **لا توجد اليوم — بحسب ما وثّقته Supabase رسميًا — واجهة مدعومة لإبطال جلسة واحدة محددة يختارها المستخدم من قائمة**؛ المدعوم هو `local` (هذه الجلسة) و`others` (كل ما عداها) و`global` (الكل). **نصرّح بذلك ولا نبني حلًا خامًا داخل جداول Auth.**
- **Supabase Auth يطبّق Rate Limits مدمجة** لكل نقطة نهاية؛ التمييز الثلاثي المعتمد: (أ) حدود GoTrue المدمجة، (ب) حدّ معدل تطبيقي داخل قاعدتنا للمسارات التي نملكها، (ج) WAF/طبقة حافة — مؤجلة لما قبل الإطلاق العام بقرار المالك.
- **إنفاذ MFA خادميًا** عبر `aal2` وسياسات RLS **Restrictive** على العمليات الحساسة، لا عبر الواجهة وحدها.
- **الاستعادة** تشمل: قاعدة البيانات + Auth + كائنات Storage وسياساتها + Edge Functions وأسرارها وإعداداتها. نسخة المشروع وحدها لا تعيد كل ذلك.
