# ADR-0001 — تثبيت المعمارية ومصدر الحقيقة (منصة ركيز)

> **الحالة:** معتمد (المرحلة 1)
> **التاريخ:** 2026-08-14 UTC
> **النطاق:** توثيق قرارات معمارية فقط — لا كود، لا Migration، لا تفعيل خدمات.

---

## 1. مصدر البيانات: Supabase مستقل

**القرار:** مشروع **Supabase مستقل وجديد تمامًا** هو مصدر الحقيقة الوحيد لبيانات المنصة. لا يُستورد أي بيانات أو مخطط من مشاريع سابقة.

**ما هو مستبعد نهائيًا:**
- Lovable Cloud كقاعدة بيانات للمشروع.
- أي تبديل تلقائي مستقبلي بين مزوّدي قواعد البيانات.
- أي مصدر بيانات ثانٍ موازٍ (لا localStorage كمخزن دائم، لا ملفات JSON ساكنة كبديل عن الجداول).

**المبررات:**
- ملكية كاملة للمشروع ولمفاتيحه وفواتيره خارج دورة حياة منصة البناء.
- حرية في إدارة الـ Migrations والنسخ الاحتياطي والامتدادات (extensions) مباشرة.
- استمرارية طويلة الأمد لمنصة عقارية/تعاقدية تتوقع نموًا في البيانات الحساسة.

**الآثار على العميل/الخادم:**
- عميل المتصفح يستخدم مفتاح publishable فقط، وكل وصول يمر عبر RLS.
- العمليات المميزة (privileged) تتم حصريًا داخل server functions على الخادم، بمفتاح سرّي لا يصل المتصفح أبدًا.
- متغيرات الاتصال تُقرأ داخل الـ handler على الخادم، ولا تُسرَّب إلى حزمة العميل.
- التفعيل الفعلي لهذا القرار يحتاج أمر Build منفصل ومعتمد صراحةً (خارج هذه المرحلة).

## 2. حدود الوحدات (Module Boundaries)

الوحدات التالية هي التقسيم المنطقي المتوقع للنظام. **لم تُنشأ أي جداول** — هذه أسماء ونطاقات مقترحة فقط.

| # | الوحدة | الاسم التقني المقترح | النطاق ومبرر الفصل |
|---|--------|----------------------|---------------------|
| 1 | الهوية والكيانات | `identity` | المستخدمون، الحسابات الشخصية، الكيانات (شركات/مكاتب/أفراد)، العضويات والأدوار. مفصولة لأنها أساس كل تحقق صلاحيات في بقية الوحدات. |
| 2 | العقارات والمشاريع | `properties` / `projects` | الأصول العقارية والمشاريع المرتبطة بها. مفصولة لأن العقار كيان طويل العمر بينما المشروع دورة حياة محددة. |
| 3 | القوالب والمراحل | `templates` / `phases` | قوالب سير العمل ومراحل تنفيذ المشاريع. مفصولة لأنها بيانات تعريفية قابلة لإعادة الاستخدام عبر مشاريع متعددة. |
| 4 | العقود والمراسلات | `contracts` / `correspondence` | العقود، الملاحق، الخطابات، والمراسلات الرسمية. مفصولة لمتطلبات إصدارات وتوقيع وتتبع صارمة. |
| 5 | المستندات والتقارير | `documents` / `reports` | الملفات المرفوعة، المرفقات، والتقارير المولّدة. مفصولة لارتباطها بالتخزين (Storage) وبسياسات وصول مختلفة عن البيانات الجدولية. |
| 6 | الخدمات والمالية | `services` / `finance` | كتالوج الخدمات، الطلبات، الفواتير، المدفوعات. مفصولة لحساسيتها المالية ولحاجتها إلى تدقيق غير قابل للتعديل. |
| 7 | الإشعارات والتدقيق | `notifications` / `audit` | إشعارات المستخدمين وسجل التدقيق الموحّد. مفصولة لأنها وحدات عرضية (cross-cutting) تُغذّى من كل الوحدات الأخرى. |

**قاعدة الحدود:** الوحدة لا تكتب مباشرة في جداول وحدة أخرى؛ التكامل يتم عبر مفاتيح أجنبية معرّفة صراحةً أو عبر طبقة خدمة على الخادم.

## 3. اصطلاحات التسمية (Naming Conventions)

- **الجداول:** `snake_case`، صيغة الجمع (`projects`, `contract_versions`, `entity_memberships`).
- **الأعمدة:** `snake_case`، مفرد وصفي (`start_date`, `total_amount`).
- **المفتاح الأساسي:** `id uuid` مع `gen_random_uuid()` افتراضيًا.
- **المفاتيح الأجنبية:** `<اسم_المفرد>_id` (`project_id`, `entity_id`, `document_id`).
- **مفاتيح النطاق (scope keys):** تُختار **حسب سياق الجدول**، بلا فرض مفتاح واحد موحّد على كل الجداول:
  - `entity_id` عندما يكون العزل على مستوى الكيان.
  - `project_id` عندما يكون العزل على مستوى المشروع.
  - `owner_id` / `user_id` عندما تكون البيانات شخصية بحتة.
  - `created_by` يُسجَّل دائمًا على الجداول القابلة للتحرير، لكنه ليس مفتاح عزل بحد ذاته.
- **الأعمدة الزمنية القياسية:** `created_at timestamptz not null default now()`، `updated_at timestamptz`، `deleted_at timestamptz` (للحذف الناعم).
- **القيم المعدودة:** أنواع `enum` في مخطط `public` بأسماء مفردة (`app_role`, `project_status`).
- **الفهارس:** `idx_<table>_<columns>`؛ فهرس إلزامي على كل مفتاح نطاق يُستخدم في RLS.
- **الدوال:** `snake_case` بفعل واضح (`has_role`, `is_entity_member`).
- **اللغة:** أسماء المخطط بالإنجليزية دائمًا؛ النصوص العربية بيانات لا أسماء أعمدة.

## 4. الهوية: `auth.users` هو المصدر الوحيد

**القرار:** جدول `auth.users` التابع لـ Supabase Auth هو المصدر **الوحيد** لهوية تسجيل الدخول. لا يوجد جدول مستخدمين موازٍ ولا مصادقة مخصصة.

**النموذج المعتمد:** مستخدم واحد ← حساب شخصي واحد ← عضويات متعددة في كيانات.

```text
auth.users (هوية الدخول)
   └── profile (حساب شخصي: الاسم، الصورة، اللغة، التفضيلات)
         └── entity_membership (عضوية) ── entity (كيان)
               └── role (دور خاص بهذه العضوية فقط)
```

**القواعد الملزمة:**
- الدور **لا يُخزَّن إطلاقًا** في `profile` أو أي جدول مستخدمين — بل في جدول عضويات/أدوار منفصل مع قيد فريد على `(user_id, entity_id, role)`.
- التحقق من الأدوار يتم عبر دوال `SECURITY DEFINER` (مثل `has_role`) لتفادي تكرار RLS.
- المستخدم قد يحمل أدوارًا مختلفة في كيانات مختلفة؛ الدور بلا سياق كيان لا معنى له.
- الحساب الشخصي يُنشأ تلقائيًا عبر trigger عند إنشاء مستخدم جديد.
- تصعيد الصلاحيات لا يتم أبدًا من العميل؛ منح الأدوار عملية خادمية محمية.

## 5. حدود العزل: Tenant / Entity / Project

**التسلسل:** `Tenant (الحساب) → Entity (الكيان) → Project (المشروع) → السجلات التفصيلية`.

**القواعد الملزمة:**
1. كل جدول يحمل بيانات غير عامة **يجب** أن يحمل مفتاح نطاق واضحًا يربطه بالتسلسل أعلاه.
2. كل استعلام يمر عبر مفتاح النطاق؛ لا استعلام مفتوح على جدول متعدد المستأجرين.
3. العزل **إلزامي**: لا يرى أي مستخدم بيانات كيان ليس عضوًا فيه، ولا مشروعًا لا ينتمي إلى كياناته.
4. `ENABLE ROW LEVEL SECURITY` على كل جدول في `public` بلا استثناء، مع سياسات صريحة لكل عملية.
5. سياسات RLS تُبنى على دوال `SECURITY DEFINER` تتحقق من العضوية والدور، لا على استعلامات متداخلة على نفس الجدول.
6. كل `CREATE TABLE` في `public` يُتبع بعبارات `GRANT` صريحة في نفس الـ migration.
7. تجاوز العزل ممكن فقط عبر مفتاح الخدمة داخل server function بعد تحقق صريح من الصلاحية.

## 6. السياسات العامة: الحذف الناعم، الإصدارات، والتدقيق

### 6.1 Soft Delete
- كل جدول حسّاس يحمل `deleted_at timestamptz null`.
- الحذف الافتراضي = تعيين `deleted_at`؛ الحذف الصلب محجوز لطلبات الخصوصية القانونية فقط.
- كل قراءة تستثني الصفوف المحذوفة (عبر السياسة أو عبر view).
- قيود التفرد تراعي الحذف الناعم (فهرس فريد جزئي على `deleted_at is null`).

### 6.2 Versioning
- العقود والمراسلات والمستندات والتقارير: **إصدارات غير قابلة للتعديل** في جدول `*_versions` بعمود `version_number`.
- السجل الأصلي يشير إلى الإصدار الحالي؛ التعديل يُنشئ إصدارًا جديدًا ولا يستبدل القديم.
- القوالب مُصدَّرة أيضًا: تغيير قالب لا يغيّر المشاريع التي استُنسخت منه سابقًا.

### 6.3 Audit Policy
- سجل تدقيق موحّد يجيب: **من فعل ماذا، متى، على أي سجل، وفي أي نطاق**.
- الحقول الأساسية: `actor_id`, `action`, `table_name`, `record_id`, `entity_id`, `before`/`after` (jsonb), `occurred_at`, `ip`/`user_agent` عند التوفر.
- سجل التدقيق **append-only**: لا `UPDATE` ولا `DELETE` عليه لأي دور تطبيقي.
- التدقيق إلزامي على: الهوية والأدوار، العقود، المالية، المستندات. اختياري على البيانات المرجعية.
- القراءة مقيّدة بأدوار إدارية داخل نطاق الكيان.

## 8. ضمانات هذه المرحلة

- لم يُنفَّذ أي migration ولم يُنشأ أي جدول.
- لم تُفعَّل أي خدمة خارجية (Supabase أو غيرها).
- لم يُعدَّل أي كود تطبيقي أو صفحة هبوط.
- لم تُلمس أي إعدادات GitHub.
- لم تُضف أي حزم أو تبعيات.
- الرجوع الكامل = حذف هذا الملف.
